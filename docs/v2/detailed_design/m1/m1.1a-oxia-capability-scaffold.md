# M1.1a-O2 Nereus metadata-oxia capability scaffold

## Status and confirmation boundary

This is the accepted code-level design for `M1.1a-O2`. It translates the accepted four-capability, exact-value,
continuity, and fail-closed contracts into Nereus module layout, classes, call paths, tests, gates, and commit order. It
does not replace [ADR 0082](../../../decisions/0082-v2-m1-domain-and-control-authority-contracts.md),
[ADR 0084](../../../decisions/0084-v2-m1-leaf-witness-registry-and-receipt-contracts.md), the normative
[metadata backend contract](../../06-metadata-backends-and-handoff.md), or the accepted
[O1 client design](m1.1a-oxia-client-continuity.md). Those authorities win on conflict.

On 2026-08-12 the user accepted this design, the five-batch implementation sequence, and the three explicit
corrections identified by the source audit:

1. qualify and consume the O1 `oxia-client` and `oxia-client-api` artifacts as one immutable bundle;
2. replace the module's old Oxia 0.9.0 dependency as a whole instead of mixing duplicate 0.9.0/0.9.4 classes;
3. correct `TopicBindingAggregateReader` so its input can deterministically reconstruct the accepted Pulsar aggregate
   authority leaf instead of attempting to locate an authority using `TopicBindingId` alone.

That acceptance authorizes only the implementation sequence at the end of this file. It does not authorize O2 to
enter P1/R1, produce a scenario PASS, or modify the Oxia server.

## Scope and non-goals

O2 adds a new V2 package tree inside the existing physical `nereus-metadata-oxia` project. The project still contains
V1 residue until the final M1 graph cut, but the new production dependency path is strictly:

```text
nereus-domain <- nereus-metadata-spi <- nereus-metadata-oxia V2 package
                                              |
                                              +-- exact O1 Oxia artifact bundle
```

O2 implements:

- the existing four SPI interfaces with one-key Oxia operations;
- an internal, exact key/envelope codec boundary;
- an internal conditional create/CAS engine with exact reread resolution;
- one process-local, store-wide continuity state and invalidation epoch;
- deterministic fake, response-loss, malformed-value, lifecycle, and race tests;
- the local `v2M1OxiaScaffoldCheck` gate.

O2 does not implement:

- complete NTA1 or a production aggregate codec;
- production selector or Registry codecs while their complete contracts remain OPEN;
- selector transition policy, ownership witness, authoritative A/read/B, ACTIVE/VALID fence, or Pulsar integration;
- Registry allocator, writer inventory/capacity, admission interlock, or `REGISTRY_CONFORMANCE`;
- Kafka K1, Pulsar P1, Registry R1, V1/KoP prune, Docker conformance, server wire/RPC, scenario promotion, N2/N3, or M1
  Final receipt.

The module exposes no broad `V2OxiaMetadataStore`, generic CRUD/list/watch API, Oxia type through an SPI signature, V1
`Stream`/`Projection`/`Profile` type, or V1 `WatchRegistration` correctness dependency.

## Exact O1 artifact consumption

### Audit finding

The final fork's continuity API lives in the separate `oxia-client-api` artifact, while the implementation lives in
`oxia-client`. The current O1 receipt locks only:

- `client-0.9.4.jar`;
- `client-0.9.4-sources.jar`;
- the client POM.

The generated client POM depends on ordinary `io.github.oxia-db:oxia-client-api:0.9.4`. The local fork build produced

### Accepted artifact contract

Before O2 production compilation, rebuild the clean O1 final fork and qualify this complete bundle:

```text
oxia-client-api-0.9.4.jar
oxia-client-api-0.9.4-sources.jar
oxia-client-api-0.9.4.pom
oxia-client-0.9.4.jar
oxia-client-0.9.4-sources.jar
oxia-client-0.9.4.pom

```

Every file receives a length and SHA-256 receipt bound to final fork `091a42c...`. The client POM/Gradle metadata must
resolve `oxia-client-api` from that same bundle; the gate rejects a graph that selects Maven Central's API artifact.

The accepted design chooses a repository-tracked, immutable Maven-style bundle at:

```text
gradle/locked-artifacts/oxia-client-java/
  091a42c2780d92da56e9ec1f02ce1c3d988adc16/m2/
```

One checked bootstrap script refuses a dirty or non-exact O1 checkout, invokes the API/client JAR, source-JAR, POM, and
Gradle-metadata tasks, copies only the expected Maven layout, and writes a sorted length/SHA-256 manifest. The bundle
and manifest are committed in the accepted artifact commit. Nereus `settings.gradle.kts` uses `exclusiveContent` with
module-level filters for only `io.github.oxia-db:oxia-client` and `io.github.oxia-db:oxia-client-api`; those two modules
cannot fall back to Maven Central. The version catalog selects `0.9.4`, and the bundle's client POM/Gradle metadata must
point to its sibling API at the same version. Other `io.github.oxia-db` modules, including testcontainers, remain
normal external dependencies.

This deliberately pays a small repository-size cost for a clean-checkout, offline-verifiable O1 dependency while an
organization-owned immutable package repository does not yet exist. A later accepted package-promotion slice may
replace the transport only if it preserves the same artifact hashes. The final contract forbids Maven Local,
`flatDir`, a mutable SNAPSHOT, a developer absolute path, an unqualified Maven Central `0.9.4`, or an environment-
selected artifact from affecting resolution. A source composite may be a separate developer diagnostic, but it is not
O2's final artifact contract.

Because `nereus-metadata-oxia` already imports the old Oxia API throughout its V1 residue, Gradle must replace the Oxia
client/API dependency for the entire module. Both versions share identical packages/class names and cannot coexist on
one compile/runtime classpath. The dependency gate inspects resolved component/artifact identities and requires exactly
one O1 client plus exactly one matching O1 client-api. Compatibility of the legacy V1 module tests with that replacement
is part of `:nereus-metadata-oxia:check`; failure stops O2 rather than adding a duplicate classloader or shaded facade.

The O1 source-lock binding is extended, never overwritten: implementation base, final fork, each API/client artifact,
server source/image, and focused result remain distinct. `sourceTupleId` stays `v2-m0`.

## Package, dependency, and composition layout

All O2 classes live under `com.nereusstream.metadata.oxia.v2`; V1 packages remain untouched:

```text
v2/
├── OxiaV2CapabilityStore.java                 # owns one AsyncOxiaClient and four adapters
├── OxiaV2CapabilityStoreFactory.java          # explicit production/fake construction; no service locator
├── OxiaV2StoreConfiguration.java              # namespace/root/deployment inputs, no V1 config type
├── continuity/
│   ├── StoreContinuity.java                   # local state/epoch snapshot and listener bridge
│   ├── StoreContinuitySnapshot.java           # CLOSED/ARMING/READY plus invalidation epoch
│   └── RevalidationScheduler.java              # coalesced non-blocking scheduling port
├── key/
│   └── OxiaV2AuthorityKeys.java                # configured root plus exact accepted leaf grammar
├── codec/
│   ├── AuthorityValueCodec.java               # narrow internal encode/decode/identity port
│   ├── AggregateAuthorityCodec.java            # fail-closed placeholder until M1.1b
│   ├── SelectorAuthorityCodec.java             # fail-closed placeholder until P1 codec exists
│   └── RegistryAuthorityCodec.java             # fail-closed placeholder until R1 codec/cap exists
├── mutation/
│   ├── OxiaConditionalClient.java              # exact get/create/CAS only
│   ├── ConditionalMutationEngine.java          # closed result resolver
│   ├── AuthorityRecord.java                    # key, bytes, backend version
│   └── MutationFailureClassifier.java          # condition-failed vs response-unknown vs definitive local invalid
└── capability/
    ├── OxiaTopicBindingAggregatePublisher.java
    ├── OxiaTopicBindingAggregateReader.java
    ├── OxiaPulsarTopicGenerationSelectorStore.java
    └── OxiaPulsarVirtualLedgerNamespaceRegistryStore.java
```

The production factory creates one `AsyncOxiaClient` and registers exactly one O1 continuity listener before exposing
the store. All four adapters borrow that same client, continuity instance, keyspace, and conditional engine. Adapters
do not close shared resources. `OxiaV2CapabilityStore.close()` is idempotent and orders shutdown as follows:

1. atomically stop admission and advance the local invalidation epoch into terminal CLOSED;
2. reject new operations and make every old operation/install token stale;
3. close the O1 `NotificationContinuityRegistration`;
4. stop/coalesce the revalidation scheduler and cancel work that has not started;
5. wait only for already accepted local completion callbacks to drain within the owned executor contract;
6. close the owned `AsyncOxiaClient` last.

The O1 callback never waits for steps 4 through 6 and never performs a remote read. If client construction or
registration fails, the factory closes already-created resources in reverse order and returns no partially live store.

## Authority keys and required SPI correction

### Physical keys

`OxiaV2AuthorityKeys` owns one validated deployment-scoped root chosen by composition, outside persisted domain wire.
Under distinct versioned prefixes it builds only:

```text
selector:  <root>/selectors/v1/<NPN1 name digest>
aggregate: <root>/aggregates/v1/<NPN1 name digest>/<generation19>
registry:  <root>/registries/v1/<deploymentIdHex>/<reservationDomainIdHex>/<namespaceIdHex>
```

The selector and aggregate leaves are exactly `PulsarAuthorityLeafCodecV1`. Registry key identity uses the exact
non-zero deployment/reservation IDs plus the 32-byte ledger compatibility namespace ID, all lowercase fixed-width
hex. The value decoder repeats and validates the corresponding typed identities. Partition routing is derived from
the same authority identity by one internal function; it is not persisted and does not create another authority.

No key is discovered with `list`, a watch cache, a binding-ID index, or a child key. Publisher and reader call the same
`aggregateKey(PulsarTopicIncarnationIdentity)` function.

### Why `readAggregate(TopicBindingId)` cannot be implemented correctly

The current reader accepts only the derived 32-byte `TopicBindingId`. The accepted Pulsar aggregate authority leaf is
derived from canonical persistence name plus binding generation. SHA-256 is not reversible, so the reader cannot
reconstruct that authority key from a binding ID. Implementing `/by-binding/<bindingId>`, listing aggregates, or keeping
a durable/cache index would introduce forbidden child/discovery authority.

The accepted correction retains exactly four capabilities but changes the method to:

```java
CompletionStage<Optional<VersionedAggregateSnapshot>> readAggregate(
        TopicIncarnationIdentity incarnationIdentity);
```

O2 supports only the Pulsar variant and rejects another protocol before I/O. The decoded aggregate must contain that
same incarnation and its deterministically rederived binding ID. The publisher derives the key from
`candidate.aggregate().binding().incarnationIdentity()`; reader and publisher therefore share one immutable authority
key without changing `AggregatePublicationCandidate` or adding a generic key parameter.

This is an SPI shape correction, not a fifth capability or a new normative authority. It requires updating foundation
tests/design references and rerunning `v2M1FoundationCheck`. User confirmation of this O2 design explicitly confirms
that correction.

## Codec boundary and fail-closed activation

`AuthorityValueCodec<K,V>` is an internal package-private port with only:

```text
authorityKey(typed identity/value) -> exact String
encode(candidate)                  -> canonical stored bytes
decode(expected key, stored bytes) -> typed value or definitive malformed failure
matchesExpected(candidate, record) -> key + schema + digest + byte equality
```

It has no generic map/list/watch methods and never appears in `nereus-metadata-spi`.

O2 must not invent complete NTA1, selector production wire, or Registry writer/capacity wire. Consequently:

- `AggregateAuthorityCodec` can be injected by deterministic tests, but its production constructor fails closed until
  the accepted M1.1b codec is supplied;
- selector and Registry adapters likewise require explicit production codec capabilities that are absent in O2;
- the factory can construct a continuity/mutation scaffold for local tests but `productionActivationReady()` remains
  false and every production adapter operation fails before Oxia I/O when the required codec is unavailable;
- opaque caller-supplied canonical bytes are never decoded by guessing a schema or trusted solely because their digest
  matches.

After later slices provide a codec, decode must enforce the expected authority key, exact known schema, strict EOF,
canonical re-encode equality, supplied SHA-256, and all repeated typed identities. Malformed input, schema mismatch,
digest mismatch, key/value mismatch, or rederived identity mismatch is a definitive fail-closed result. The adapter
never overwrites, repairs, canonicalizes, or returns such a record as exact.

## MetadataVersion mapping

Oxia `Version.versionId()` is a non-negative `long` used only for exact conditional writes. The adapter maps it to
`MetadataVersion` as exactly eight unsigned big-endian bytes. Decode accepts only eight bytes and a non-negative long;
no timestamp, modification count, session/client ID, notification offset, shard, or provider identity enters the SPI
version. CAS converts that exact eight-byte value back to `PutOption.IfVersionIdEquals(long)`.

The version belongs to the same exact authority record as the canonical bytes. A predecessor whose decoded key/value
identity, stored bytes, digest, or version does not match the target key is rejected before dispatch.

## Conditional mutation engine

`OxiaConditionalClient` exposes only exact `get`, `createIfAbsent`, and `compareAndSet` against one already validated
key. The production implementation wraps `AsyncOxiaClient`; deterministic tests supply a fake. There is no range/list,
delete, unconditional put, watch, retry loop, or V1 backend reuse.

The engine classifies completions after unwrapping `CompletionException`/`ExecutionException`:

- `KeyAlreadyExistsException` and `UnexpectedVersionIdException` are condition failures and require exact reread;
- cancellation, timeout, transport, session, unavailable, and other failures after dispatch are response-unknown and
  require one bounded exact reread;
- local validation/codec/key/version failures occur before dispatch and fail definitively;
- a failed reread or malformed record yields `INDETERMINATE` to the SPI caller and separately raises a fail-closed
  diagnostic; it never produces an exact snapshot.

Create resolution is:

```text
putIfAbsent success
  -> exact reread of the same key
  -> exact candidate record => CREATED
  -> any other/absent/malformed/unreadable result => INDETERMINATE

condition failure or response unknown
  -> exact reread
  -> exact candidate record => EXISTING_EXACT
  -> well-formed different authority value => DEFINITIVE_CONFLICT
  -> absent, malformed, identity mismatch, or unreadable => INDETERMINATE
```

CAS resolution is:

```text
putIfVersion success
  -> exact reread
  -> exact candidate record => APPLIED_EXACT
  -> otherwise => INDETERMINATE

condition failure or response unknown
  -> exact reread
  -> exact candidate record => APPLIED_EXACT
  -> exact predecessor key/version/bytes unchanged => PREDECESSOR_UNCHANGED
  -> well-formed different authority value => DEFINITIVE_CONFLICT
  -> absent, malformed, identity mismatch, or unreadable => INDETERMINATE
```

This deliberately avoids assuming that a successful RPC's returned version proves stored byte equality. The exact
reread is bounded to one same-key operation; it has no internal retry. The caller may retry only from a closed result.

All four adapters use this one engine. Aggregate is create/read only. Selector and Registry expose one-key
read/create/CAS scaffold but no lifecycle transition, allocator, ownership, or writer-admission policy.

## Store-wide continuity and stale-install protection

`StoreContinuity` owns one atomically published immutable local word:

```text
StoreContinuitySnapshot(
    lifecycle = ARMING | READY | CLOSED,
    clientGeneration,
    invalidationEpoch)
```

`invalidationEpoch` is process-local, positive, monotonically increasing, never persisted, and not exposed through the
metadata SPI. Its mapping rules are:

- initial O1 snapshot, ARMING, first observed generation, any generation change, duplicate/later loss, and CLOSED all
  publish fail-closed state;
- every distinct O1 generation not previously invalidated advances the epoch exactly once before recovery is queued;
- CLOSED advances/retains the terminal epoch and can never return READY;
- READY for the current generation changes only lifecycle state and schedules authoritative reread; it never grants
  ACTIVE/VALID or decrements/reuses the epoch;
- stale/duplicate older-generation callbacks cannot regress state or schedule installation.

Construction closes the listener-registration race as follows:

1. initialize the local word to fail-closed;
2. call `AsyncOxiaClient.notificationContinuity(listener)`;
3. while still unpublished to callers, reconcile `registration.current()` through the same serialized transition
   function used by the listener;
4. expose the store only after the registration handle is owned and the reconciled word is visible.

The O1 contract enqueues the registration's initial snapshot before a concurrent loss, but O2 still treats duplicate
and reordered observations defensively by generation/state. Registration failure closes the client and returns no
store.

The callback does constant-time local work only: atomic state/epoch publication plus a non-blocking coalesced
`RevalidationScheduler.request(generation, epoch)`. It performs no Oxia get/put, no Pulsar metadata read, no blocking
join, no sleep/backoff, and no user callback. Queue saturation remains fail closed and is reported; it cannot restore
READY.

Future P1 installers capture an `InstallPermit(generation, invalidationEpoch)` only from current READY and must
compare-and-set the exact expected local word after authoritative A/read/B. O2 provides the package-internal permit and
final compare primitive so tests can prove stale installers fail, but it does not implement A/read/B or an ACTIVE
fence. Any ARMING/generation change/CLOSED advances or changes the word before recovery runs, so the old permit's final
CAS fails. In-flight metadata mutations may complete with their closed storage result, but their old continuity permit
cannot authorize runtime installation.

Different `OxiaV2CapabilityStore` instances own independent continuity words, registrations, schedulers, clients, and
close lifecycles. Static mutable continuity state is forbidden.

## Test plan

All local tests use deterministic fakes and run without Docker. Required suites have non-zero discovery and zero
failure/skip/abort.

### Artifact and dependency tests

- exact O1 client and client-api bundle hashes, POM edges, final-fork identity, and source-lock bindings;
- resolved `nereus-metadata-oxia` graph contains one O1 client/API pair and no ordinary 0.9.0/0.9.4 duplicate;
- no Maven Local, mutable SNAPSHOT, absolute path, `flatDir`, or unqualified Maven Central fallback;
- clean-checkout resolution does not require the sibling O1 worktree.

### Key, codec, and version tests

- selector/aggregate leaves match NPN1/generation19 goldens and key/value names/generation;
- Registry key binds exact deployment, reservation domain, and namespace digest;
- publisher and reader produce the same aggregate key from the same Pulsar incarnation;
- eight-byte big-endian `MetadataVersion` boundary, negative/wrong-length rejection;
- malformed bytes, unknown schema, strict-EOF failure, digest mismatch, noncanonical bytes, protocol/name/generation/
  binding/Registry identity mismatch all fail closed without a repair write;
- missing production aggregate/selector/Registry codec blocks activation before backend I/O.

### Conditional engine and four adapters

- aggregate publish/read: absent, created, existing exact, conflicting value, response loss, failed reread;
- selector and Registry read/create/CAS: success, condition conflict, response loss, exact candidate, exact unchanged
  predecessor, definitive conflict, indeterminate;
- create/CAS success responses are still exact-reread verified;
- condition/unknown classification unwraps nested async failures;
- every adapter uses exactly one authority key, never list/watch/delete/unconditional put;
- Binding and initial Epoch projections come from the same returned `VersionedAggregateSnapshot` object.

### Continuity, close, and race tests

- initial/ARMING to READY queues revalidation but grants no ACTIVE state;
- READY to new generation invalidates before scheduling recovery;
- repeated loss, reassignment, stale/duplicate callback, and CLOSED remain monotonic/fail closed;
- listener callback versus `registration.current()` construction race;
- READY versus close, close idempotency, and listener deregistration order;
- in-flight operation result versus close/invalidation;
- a stale install permit cannot publish after loss even if its remote future completes later;
- callback performs no remote operation and does not block a controlled O1 callback thread;
- two stores remain isolated under loss and close.

The test report records discovered, executed, passed, failed, skipped, and aborted totals. This is local scaffold
evidence only and cannot be called real Oxia, Pulsar, ownership-witness, Registry, or scenario conformance.

## Commit and push sequence after confirmation

Each batch checks its exact staged paths, runs the relevant local gate, commits, and pushes `main` before the next batch:

1. accept this design, correct the aggregate-reader shape, and freeze the complete O1 artifact-bundle mechanism;
2. bind/consume the O1 client+API pair and implement store-wide continuity/close scaffolding;
3. implement the narrow conditional engine, key/version boundary, fail-closed codec ports, and four adapters;
4. add deterministic fakes, response-loss/continuity/race tests, dependency/source checks, and
   `v2M1OxiaScaffoldCheck`;
5. synchronize current docs and focused evidence, run clean final verification, then commit/push evidence only.

No batch uses force push, reset, history rewrite, unrelated staging, or a server/client-fork code change. If a mandatory
gate fails, the failing batch is not represented as complete and later batches do not start.

## Completion boundary

O2 is complete only when the exact O1 artifact bundle resolves reproducibly, the corrected four SPI capabilities have
one-key adapters, all production codec gaps fail closed, continuity invalidates before recovery and rejects stale
installers, all deterministic tests/gates pass with non-zero counts, docs/source-lock evidence is current, and every
authorized commit is pushed.

Even then O2 does not prove P1/R1/M1: it has no ownership witness or A/read/B, no selector transition kernel, no Registry
writer/capacity/interlock, no complete NTA1/selector/Registry production codec, no real Oxia/Pulsar conformance, and no
trusted promotion receipt. The next implementation slice must be separately authorized.
