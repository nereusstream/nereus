# M1.1c-R0 Registry writer-count and canonical-capacity spike

## Status and authority boundary

This is the code-level design for the evidence-only Registry-capacity slice that precedes R1. It freezes the spike
inputs, accounting model, cohort lifecycle, deterministic scenarios, rejection taxonomy, evidence shape, and delivery
order. Eighteen focused tests and `v2M1RegistryCapacityCheck` reproduce the committed evidence at Nereus
`03d272567595c77051af3c473b4dbca8999d79d2`; the synchronized accepted ADRs therefore consume the resulting numeric
boundary as an R1 input. This verification is readiness evidence only, not R1 production authority or conformance.

[ADR 0032](../../../decisions/0032-v2-pulsar-virtual-ledger-reservation-registry.md),
[ADR 0054](../../../decisions/0054-v2-pulsar-virtual-ledger-bootstrap-geometry.md), and
[ADRs 0082 through 0085](../../../decisions/0082-v2-m1-domain-and-control-authority-contracts.md) remain normative.
They win if this design conflicts with them. The spike does not implement or activate the R1 Registry codec, Store,
writer interlock, allocator mode, derived slice view, or real Oxia conformance.

## Scope and non-goals

The slice may add only test/evidence code, a deterministic generated report, a fast gate, and synchronized documents.
It must:

- use the two closed writer kinds and the exact 120-byte row already accepted by ADR 0085;
- model a row as one source-qualified writer cohort under one independently revocable principal generation, never as
  one broker or process;
- retain the existing 65,536-byte Registry envelope, 256 lifetime assignments, and 192-byte full assignment-row
  contribution without redefining any of them;
- compute the maximum from checked arithmetic and concrete lifecycle scenarios rather than assuming
  `maxWriterCount=8`;
- cover omission, unauthorized writers, add-before-start, and fence/drain/revoke/remove ordering;
- emit deterministic JSON and Markdown marked non-promotable and non-conformant.

The slice must not add a production Registry value model, encoder, parser, validator, error class, transition kernel,
interlock, Oxia codec, Store behavior, allocator SPI/mode, per-rollover Registry read, K1/P1, V1 prune, M2 runtime,
10k/100k benchmark, scenario promotion, `REGISTRY_CONFORMANCE`, or M1 PASS claim. In particular,
`OxiaV2CodecSet.productionAggregateOnly()` must retain an unavailable Registry codec.

## Frozen spike inputs

The harness consumes this closed input table:

| Input | Value | Source and interpretation |
| --- | ---: | --- |
| writer kinds | 2 | native BookKeeper ledger-ID and Nereus virtual-ledger-ID allocation |
| writer row | 120 bytes | exact fixed ADR 0085 row, including its typed evidence reference |
| Registry envelope | 65,536 bytes | inherited ADR 0054 hard compatibility envelope |
| lifetime assignments | 256 | every ACTIVE, RETIRING, and RETIRED assignment counts |
| assignment-row hard maximum | 192 bytes | full canonical contribution of one row, including any row-local framing |
| slice exponent | 40 | inherited bootstrap geometry |
| conditional metadata version | 8 bytes | exact O2 `MetadataVersion`/Oxia expected-version operand |

The 192-byte assignment limit is not changed to 190 or 194. R1 must fit any row-local length framing inside the
existing 192-byte full-row contribution; the capacity formula adds no hidden per-row prefix outside that limit.

## Canonical capacity-accounting layout

R0 freezes only the widths needed to prove the complete Registry maximum. It does not supply a production encoder or
claim that opaque O2 bytes are now decodable. The R1 canonical value must account for the fixed header below, followed
by fixed writer rows and self-framed assignment rows:

```text
field                                                   bytes
NVR1 capacity-accounting magic                              4
u16 schemaVersion                                           2
deploymentId                                               16
reservationDomainId                                        16
canonicalInstanceIdAscii                                   36
ledgerIdCompatibilityNamespaceId                           32
u64 reservedStartInclusive                                  8
u64 reservedEndInclusive                                    8
u16 sliceExponent                                           2
u32 maxRegistryBytes                                        4
u16 maxAssignmentsEver                                      2
u16 maxAssignmentRowBytes                                   2
u16 maxWriterCount                                          2
u16 writerRowBytes                                          2
u64 registryEpoch                                           8
u16 registryAdmissionEvidenceKind                           2
u16 registryAdmissionEvidenceVersion                        2
registryAdmissionEvidenceSha256                             32
u16 writerCount                                             2
u16 assignmentCount                                         2
                                                        ------
fixedHeaderBytes                                           184
```

The header repeats the complete Registry key identity, exact admitted INSTANCEID and derived namespace identity,
fixed numeric domain and bootstrap limits, epoch, whole-activation evidence reference, and the two table counts. Values
that are derivable from these bytes, such as writer-set SHA, assignment-table SHA, total length, or canonical-value
SHA, are not persisted again. Exact reread compares canonical bytes; the SPI's `canonicalStoredDigest` and the receipt
remain derived integrity facts rather than a self-hash field.

The exact checked formula is:

```text
canonicalRegistryBytes =
    184
  + multiplyExact(writerCount, 120)
  + sumExact(assignmentRowCanonicalBytes[i])

0 <= writerCount
0 <= assignmentCount <= 256
0 <= assignmentRowCanonicalBytes[i] <= 192
```

Writer rows are sorted by the ADR 0085 tuple. Assignment rows are sorted by `startInclusive`. Counts, each row bound,
the checked sum, the derived legal maximum, and the inherited 65,536-byte envelope are all validated before any
allocation or backend mutation.

## Bounded cohort inventory

The spike admits concurrent binary and credential transitions and therefore measures their full two-by-two matrix.
For each writer kind, the maximum supported topology has seven distinct rows:

1. the steady source/principal cohort;
2. the second binary cohort committed before start;
3. and 4. the additional binary-by-credential combinations while two binaries and two independently revocable
   principal generations coexist;
5. one rollback cohort with a fresh principal generation;
6. one fenced-but-not-cleaned residue retained through drain and independent revocation;
7. at most one allocation-capable bootstrap/admin cohort.

A control-only admin principal with no ledger-ID allocation capability is interlock evidence, not a writer row. An
admin/bootstrap principal that can allocate IDs must occupy the applicable writer-kind row. There is no generic admin
writer kind. The same seven-slot bound is applied to both closed kinds, so the accepted executable bound is
`2 * 7 = 14` rows. This is a topology bound, not a byte-budget guess. A deployment may serialize rollouts and use fewer
rows, but it may not enlarge the format cap.

The deterministic scenario ladder is:

| Scenario | Rows | Required fact |
| --- | ---: | --- |
| steady native BookKeeper | 1 | one cohort covers all admitted native processes for one principal generation |
| steady Nereus virtual ledger | 1 | one cohort covers all admitted Nereus processes for one principal generation |
| combined steady state | 2 | both kinds are complete and independently revocable |
| old/new binary coexistence | 4 | old and new binaries never share a revocation identity |
| concurrent binary and credential rotation | 8 | full two-by-two matrix is explicit, not hidden in one row |
| rollback | 10 | rollback uses fresh generations and does not resurrect a revoked principal |
| fenced residue | 12 | fenced/draining rows remain until drain and revoke finish |
| allocation-capable bootstrap/admin | 14 | at most one separately revocable cohort per kind |
| omitted or fifteenth writer | reject | remaining byte headroom cannot override membership/count safety |

## Cohort lifecycle and admission cuts

Lifecycle is evidence/predecessor state and is not added to the 120-byte row. The harness models
`PRESTART_COMMITTED`, `ACTIVE`, `FENCED_DRAINING`, and `REVOKED_PENDING_REMOVAL`; a removed cohort is absent from the
candidate set.

Addition is ordered:

```text
qualify source and independent principal
-> add exact canonical row and evidence section
-> apply exact Registry CAS
-> verify interlock admits that exact generation
-> start the writer
```

Removal is ordered:

```text
fence allocation
-> drain accepted work
-> independently revoke the principal generation
-> retain row while cleanup/evidence is incomplete
-> remove exact row by Registry CAS
```

An allocation-capable inventory member missing from the canonical set is rejected even when the writer count and byte
formula fit. A row whose source, evidence section, principal generation, or interlock cannot be qualified is likewise
rejected. A fenced residue still consumes one row until the final remove succeeds. Response uncertainty is outside the
capacity harness and remains exact-reread R1 behavior.

## Expected maximum and rejection boundary

The focused harness derives, rather than merely printing, the following accepted readiness result:

```text
fixed header                                    184
14 writer rows * 120                          1,680
256 assignment rows * 192                    49,152
                                              ------
maximum canonical Registry value             51,016 bytes

inherited Registry envelope                  65,536 bytes
reserved envelope margin                     14,520 bytes
CAS expected-version operand                      8 bytes
maximum value plus CAS version operands      51,024 bytes
```

The Oxia value and the CAS candidate-value operand are both the exact 51,016 canonical bytes at the boundary. The
51,024 figure adds only the eight-byte expected-version operand. Configurable authority-key bytes and protobuf/gRPC
framing are deliberately excluded and must not be presented as an exact network-packet size or real Oxia conformance.

The inherited 65,536-byte envelope remains unchanged. The derived 51,016-byte maximum is the largest legal v1 value
under all closed component bounds; the 14,520 bytes are reserved compatibility margin, not a pool for extra writers,
assignments, hidden fields, or a future row expansion. A future schema must reopen the contract rather than consume
that margin silently.

The stable machine rejection codes to be consumed later by R1 are:

```text
REGISTRY_WRITER_COUNT_EXCEEDED
REGISTRY_CANONICAL_BYTES_EXCEEDED
REGISTRY_ASSIGNMENT_COUNT_EXCEEDED
REGISTRY_ASSIGNMENT_ROW_BYTES_EXCEEDED
REGISTRY_OMITTED_AUTHORIZED_WRITER
REGISTRY_UNAUTHORIZED_WRITER
REGISTRY_WRITER_LIFECYCLE_VIOLATION
```

At 14 writers, exactly 51,016 bytes is admitted. A fifteenth writer is rejected with
`REGISTRY_WRITER_COUNT_EXCEEDED` before mutation even though 51,136 bytes remains below the inherited envelope.
Exactly 51,017 canonical bytes is rejected with `REGISTRY_CANONICAL_BYTES_EXCEEDED`. More than 256 assignments and a
193-byte assignment row retain their own earlier, more specific errors.

## Test and evidence plan

The test-only harness lives under `nereus-domain/src/test` and may use real V2 identity/digest value types. It owns no
production package or main-source reference. Required focused tests cover:

- exact 120-byte writer encode and fixed-header field sum;
- every scenario row count and canonical byte breakdown;
- writer ordering, duplicates, cross-kind principal reuse, zero generations/digests, and unknown codes;
- full binary-by-credential overlap, rollback with fresh generation, fenced residue retention, and admin classification;
- missing/unauthorized writers, add-before-start, and fence/drain/revoke/remove ordering;
- checked add/multiply overflow, 14/15 writer and 51,016/51,017 byte boundaries;
- 256/257 assignment and 192/193 row boundaries;
- deterministic repeat rendering and committed JSON equality;
- absence of production Registry codec/store/allocator/runtime activation and unchanged scenario status.

The committed JSON records the Nereus source commit, immutable inputs, formula, header and table breakdown, scenario
counts, errors, Oxia value/CAS operands, margin, test totals, limitations, and digest. The companion Markdown records
the same result and artifact SHA. Both use `REGISTRY_CAPACITY_READINESS_ONLY`, `promotionEligible=false`,
`registryConformance=false`, and `scenarioPromotion=false`. They are not a virtual-ledger receipt and must not use
`REGISTRY_CONFORMANCE` or `HARNESS_CONFORMANCE_ONLY`.

The independent `v2M1RegistryCapacityCheck` must fail on zero tests, any failure/error/skip, nondeterministic output,
committed/generated mismatch, overflow, boundary drift, omitted-writer acceptance, lifecycle-order drift, source/digest
drift, production-source references, production codec availability, or scenario promotion.

## Delivery order and stop conditions

1. land this design and the non-promotion boundary (complete);
2. add the test-only model, focused tests, deterministic JSON renderer, and fast gate (complete at `03d27256`);
3. bind the harness implementation commit and generated artifact, then synchronize ADRs, execution index,
   implementation plan, scenario Markdown/JSON, open questions, README, source locks, and documentation checker
   (complete when this closeout passes all documentation and M1.1c gates);
4. only a later separately reviewed R1 slice may implement the production Registry authority against the accepted
   limits.

Stop rather than freeze the result if the harness cannot reproduce the full scenario inventory, if any required
cohort cannot be bounded by the seven-slot-per-kind model, if the formula conflicts with an accepted 120/192/256/
65,536 contract, or if evidence would require a production Registry codec, allocator selection, real Oxia claim,
scenario promotion, or M2 scale work.
