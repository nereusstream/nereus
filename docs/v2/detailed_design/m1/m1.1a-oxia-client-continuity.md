## Role, authority, and exclusions

This design translates accepted continuity semantics into Java API shape, class changes, synchronization, tests, and
delivery order. It does not replace [ADR 0084](../../../decisions/0084-v2-m1-leaf-witness-registry-and-receipt-contracts.md),
[ADR 0085](../../../decisions/0085-v2-m1-foundation-start-and-deferred-codec-bounds.md), or the normative
[metadata backend contract](../../06-metadata-backends-and-handoff.md). Those documents win on conflict.

O1 exposes only an Oxia-client-local, store-wide notification-stream lifecycle. The Oxia client API and implementation
must contain no Nereus `ACTIVE`/`VALID` fence, selector or aggregate read, A/read/B workflow, persisted
`WatchContinuityEpoch`, Pulsar ownership term, MetadataStore adapter, or Nereus metadata I/O. O1 adds no server RPC,
proto field, durable cursor, polling loop, session authority, or server/storage change.

O1 does not implement `nereus-metadata-oxia`, P1, NTA1, Registry, V1 graph deletion, or any M1 aggregate gate. Its
focused evidence cannot promote `V2-META-006` to `PASSED_CURRENT_SOURCE`.

### Java client notification and lifecycle changes

The following files are byte-identical between the locked client base and the latest candidate:

- `NotificationManager.java` and `NotificationManagerTest.java`;
- `ShardNotificationReceiver.java` and `ShardNotificationReceiverTest.java`;
- `client.proto`, including the old `io.streamnative.oxia.proto.OxiaClient` service, optional
  `start_offset_exclusive=2`, and map-form `NotificationBatch.notifications=4`.

Current behavior therefore remains:

- notification streams start lazily on the first payload callback registration;
- every initial receiver requests with no start offset;
- the first batch is treated only as an ordinary batch and is not surfaced as a ready barrier;
- `onError` retries the same receiver after backoff and retains its last offset;
- `onCompleted` immediately restarts with that offset;
- leader reassignment closes one receiver and carries its offset to the replacement;
- receiver/client close provides no loss callback and does not cancel a gRPC call through a registration handle;
- there is no generation isolation, all-shard-ready aggregation, or callback exception isolation.

These facts explain why existing notifications are useful payload delivery but do not prove V2 continuity.

The latest client adds shared transport/batcher resources and rate-adaptive read/write batching. In the paths relevant
to O1:

- `GrpcRpcProvider` may borrow a shared `ConnectionManager` and no longer always closes that manager;
- `ShardManager` adds `removeCallback`, and shared clients detach managers during close;
- `AsyncOxiaClientImpl` can borrow the executor, connection pool, and shard-assignment stream;
- `gradle.properties` advances from `0.9.0` to `0.9.4`;
- the only catalog-version change is lightproto `0.6.6 -> 0.8.0`; gRPC remains `1.75.0`, Netty `4.1.131.Final`, and
  OpenTelemetry `1.63.0`.

`GrpcRpcProvider.getNotifications` itself is unchanged at the candidate base. It has an infinite Failsafe retry around
a first-message barrier: before the first batch, retryable connection failures keep the receiver unready and are hidden
from `ShardNotificationReceiver`; after the first batch, an error reaches the receiver. `BarrierStreamObserver`
completes its internal RPC barrier before delegating the first `onNext`. The current `void`/plain-`StreamObserver`
contract also gives `ShardNotificationReceiver.close()` no way to cancel the active gRPC call.

Those two facts are implementation seams, not semantics to preserve. O1 must put notification retry ownership in the
store-wide continuity state machine, make one notification attempt cancelable, and add its semantic first-batch barrier
in `NotificationManager`/`ShardNotificationReceiver`. It must not reuse the RPC establishment future as a permanent
continuity guarantee or retain an opaque retry that can begin before loss is observable.

### Current server notification and storage changes

The current server still implements the required no-offset behavior. Under the leader lock,
`GetNotifications` reads the current commit offset and synchronously emits:

```text
NotificationBatch {
  shard = current shard
  offset = current commit offset
  timestamp = 0
  notifications = empty
}
```

Only after that send succeeds does it begin dispatching later offsets. A supplied `start_offset_exclusive` continues
from the next notification and receives no dummy. The no-offset dummy therefore remains a valid stream-armed barrier.

Important changes since v0.9.0 include:

- the leader notification implementation moved from a gRPC stream to a callback abstraction and now participates in
  leader-operation draining during close;
- notifications can be disabled per term/namespace and errors use the current standardized status mapping;
- a failed dummy send stops the dispatcher rather than leaving a background loop;
- notification recovery initializes from the last notification offset rather than an unrelated commit-offset fact;
- notification reads are bounded and notification serialization is deterministic by construction;
- public RPC authority validation and leader-hint/connection behavior were added outside the notification wire;
- the server package moved from `io.streamnative.oxia.proto` to `io.oxia.proto.v1`.

The package rename does not strand the current Java client. The server registers both services, and the explicit
compatibility service maps old `/io.streamnative.oxia.proto.OxiaClient/GetNotifications` calls to the same current
implementation. The compatibility service was introduced by `c064f99d0406796e340478085db22447f279cc22` specifically
to support older clients during the package transition.

One notification payload representation changed after server v0.16.3: field 4 moved from
`map<string, Notification>` to sorted repeated `NotificationEntry`. It is wire-compatible because a protobuf map entry
is exactly the same key/value submessage. The current Java client still decodes field 4 as a map. The exact-source
probe below verifies both the old service mapping and a non-empty current-server payload, so this conclusion is not
based only on field-number inspection.

## Phase B: selected client API

### Candidate comparison

| Candidate | Strength | Failure mode / cost | Decision |
| --- | --- | --- | --- |
| immutable continuity snapshot plus listener | repeated ready/loss/close events; generation can be compared atomically | needs race-free registration and explicit deregistration | selected |
| per-generation ready stage/future | directly represents ADR 0085's ready future and composes with async callers | a completed future cannot report later loss; a single permanent future is unsafe | selected only as a field of each generation snapshot |
| registration handle | gives deregistration and atomic access to current snapshot | adds one small API type | selected |
| client-internal capability only | smallest published surface | O2 would need implementation casts or internal-package coupling | rejected |
| public `client-api` capability | provider-neutral and consumable by a separately built adapter | carries compatibility and documentation obligations | selected for async client only |

The selected public surface is conceptually:

```java
public enum NotificationContinuityState {
    ARMING,
    READY,
    CLOSED
}

public record NotificationContinuitySnapshot(
        long generation,
        NotificationContinuityState state,
        CompletionStage<Void> readyStage) {}

public interface NotificationContinuityRegistration extends AutoCloseable {
    NotificationContinuitySnapshot current();
    @Override void close();
}

// AsyncOxiaClient
NotificationContinuityRegistration notificationContinuity(
        Consumer<NotificationContinuitySnapshot> listener);
```

These public names and semantics are accepted. The returned stage is a non-completable view owned by the client. It is
created once per generation, completes only when that exact generation becomes
store-wide ready, and completes exceptionally if the generation is lost before readiness. A successful old stage says
nothing about current continuity. Consumers must retain the generation and listen for later snapshots.

`SyncOxiaClient` is not changed. O2 consumes `AsyncOxiaClient`, and duplicating a blocking continuity API would expand
surface without adding correctness. Existing `notifications(Consumer<Notification>)` remains source/behavior
compatible and continues to deliver payloads.

The Oxia API uses only `notification`, `continuity`, `generation`, `arming`, `ready`, and `closed`. It contains no
Nereus fence/epoch, selector, aggregate, ownership, Pulsar, or A/read/B term. O2 may map an Oxia generation into its own
local `WatchContinuityEpoch`, but that mapping is outside this repository and outside O1.

## Ready and generation state machine

### States and generation ownership

`NotificationManager` owns one positive, process-local `long generation`, one immutable current-assignment shard-ID
set, one ready-shard set, one per-generation ready stage, and one current snapshot.

| Event | Old state | Linearized new state | Work allowed after publication |
| --- | --- | --- | --- |
| first payload or continuity registration | not started | generation 1 / `ARMING` | open one fresh no-offset receiver per current shard |
| first accepted batch for one shard | `ARMING(g)` | mark that shard ready in `g` | deliver that batch's payload normally |
| all non-empty current assignment shards ready | `ARMING(g)` | `READY(g)` and complete `readyStage(g)` | adapter may begin authoritative reread for `g` |
| error, completion, unknown reconnect, or assignment change | `ARMING/READY(g)` | generation `g+1` / `ARMING`; fail old pending stage | only after loss publication, recreate all current receivers with no offset |
| shard-assignment stream interruption | `ARMING/READY(g)` | generation `g+1` / `ARMING`; fail old pending stage | close notification receivers and wait for a fresh complete assignment snapshot |
| shard-assignment stream restored | `ARMING(g)` | retain `g`, install the fresh assignment snapshot | open fresh no-offset receivers; no stale assignment may arm the generation |
| client/manager close | any live state | generation `g+1` / `CLOSED`; fail pending stage | no retry or new receiver |

Generation increments use checked monotonic arithmetic. Overflow fails terminally closed; it cannot wrap and revive an
old receiver. Generation, assignment, shard identity, offset, connection, session, and ready state are never persisted.

An empty assignment is not vacuously ready. It remains `ARMING` until a non-empty current assignment is installed and
all its receivers have observed a first batch.

### First-batch semantics

A receiver is tagged with the manager generation and its exact receiver identity. Its first accepted
`NotificationBatch` performs these operations:

1. under the manager state lock, reject the batch if manager generation, receiver identity, or assignment no longer
   matches;
2. mark that shard ready for the current generation;
3. if this completes the current assignment, atomically install `READY(g)` and complete `readyStage(g)`;
4. outside the state lock, account and deliver every notification in the same batch through the existing payload
   callback path.

Therefore an empty dummy makes the shard ready, while a non-empty first batch both makes it ready and preserves every
payload. A stale first batch does neither and is dropped in full. Ready means only that all current notification
streams are armed at their observed barriers; it is not a permanent no-gap proof and grants no metadata authority.

### Assignment changes and assignment-stream continuity

`ShardManager` currently updates its assignment container before invoking change callbacks, but it publishes neither
assignment-stream interruption/restoration nor a readable continuity state. An empty change callback after reconnect
is therefore insufficient: a shared-resource client could bootstrap from stale assignments while the assignment stream
is down, and a reconnect with the same final map would not tell O1 that the observation gap ended.

O1 adds an internal, process-local `ShardAssignmentContinuitySnapshot` plus listener registration to `ShardManager`.
The snapshot contains only a monotonically increasing local generation, `ARMING | READY | CLOSED`, and the immutable
full current shard assignment; it is not part of `client-api` and is never persisted. `onError`/`onCompleted` publishes
`ARMING` before scheduling assignment-stream retry. The first complete `onNext` after reconnection updates the
assignment container and atomically publishes `READY` with the full assignment, even if the added/removed/reassigned
sets are empty. Registration returns the current snapshot and cannot miss a concurrent transition.

`NotificationManager` starts or remains armed only from an assignment `READY` snapshot. Assignment-stream `ARMING`
advances the notification generation, publishes notification `ARMING`, closes every notification receiver, and opens
none. Assignment restoration or any add/remove/reassignment installs the new complete assignment and creates fresh
no-offset receivers for every current shard. Rebuilding all shards is conservative but makes the proof simple: no
receiver admitted under an old or unconfirmed assignment can complete the new notification generation, and existing
offsets cannot cross the assignment cut. A restoration after one already-published loss retains the current
notification generation rather than emitting a second loss-only generation.

### Loss and retry ordering

The following events are discontinuities:

- receiver `onError` after a stream has reached the receiver;
- receiver `onCompleted`, whether before or after ready;
- transport/connection failure surfaced on that stream;
- leader reassignment or shard add/remove;
- client/manager close;
- any retry/reconnect for which end-to-end continuity is not proven.

The first callback matching the current `(generation, receiver)` advances the whole-store generation. Duplicate or
late error/completion callbacks from old receivers are ignored. All old receivers are canceled, all offsets are
discarded, and one manager-owned retry uses new receivers and no-offset streams. A single store-wide backoff increases
across failed generations and resets only when the whole assignment becomes `READY`; receivers own no independent
backoff or scheduled retry.

Loss publication is ordered before retry: under the manager lock, `current()` first becomes the new `ARMING(g+1)` and
that snapshot is enqueued on one serial continuity dispatcher; only then may the manager schedule receiver recreation.
The dispatcher preserves `ARMING` before any later `READY` callback, but retry does not wait for arbitrary user listener
code to return. The callback performs only local, nonblocking invalidation/scheduling; it must never perform Nereus
metadata I/O. Listener exceptions are caught, logged, and isolated so they cannot suppress other listeners or retry.

For notifications only, `GrpcRpcProvider` performs one cancelable stream attempt and forwards pre-first-batch error or
completion to the tagged receiver. The receiver routes it to the manager; the manager publishes loss and owns the next
attempt. This removes the current nested/opaque pre-first retry and makes `close()` cancel the actual gRPC call. O1 does
not change connection pooling, retry policy for any other RPC, proto, wire, or server.

## Registration, threading, close, and callback rules

Registration is linearized under the manager state lock and the atomic `ShardManager` continuity snapshot:

1. reject registration after close;
2. install a registration object;
3. start generation 1 if this is the first payload/continuity subscriber, but open receivers only if the assignment
   snapshot is `READY` and non-empty;
4. enqueue the current snapshot before any later transition can be enqueued;
5. return the handle.

`current()` performs an atomic current-snapshot read. The listener sees monotonically ordered snapshots from the
manager's serial dispatcher. Deregistration is idempotent: it marks the handle closed before removal, and queued
callbacks check that marker. Deregistering one listener does not stop payload delivery or other continuity listeners.

The serial dispatcher is backed by the existing client async executor, including shared-resource mode; it is not a
new thread per client. It never holds the manager state lock while invoking listeners. Listener blocking is forbidden
by API contract. Callback exceptions are isolated. `AsyncOxiaClientImpl.close` detaches shared shard callbacks first,
then closes `NotificationManager`, waits for its already-queued terminal publication to drain, and only then shuts down
an owned executor. Borrowed executors remain owned by `SharedResources`.

Close is idempotent. It advances generation and installs `CLOSED` before canceling receivers or retry tasks, so late
batches cannot restore ready. Each receiver extends the existing cancelable-observer mechanism; close cancels the
active gRPC call, and a scheduled manager retry holds a cancelable task handle. Registration handles remain queryable
and report the terminal snapshot, but no new listener can register. No callback executes Nereus metadata I/O or on a
server thread.

## Authorized commit and push sequence

The work is intentionally not held for one final commit:

1. Nereus: accept this design and exact implementation/conformance bases; update source-lock schema without claiming
   final fork/artifacts; run documentation/foundation gates; commit and push.
2. Oxia client: add the public API and compatibility tests; run the API/focused gates; commit and push the dedicated
   branch.
3. Oxia client: implement manager/receiver generation and ordering, complete fault/race tests, run full checks; commit
   and push again.
4. Oxia client: clean-worktree exact-runtime rerun and artifact build; record final fork and artifact hashes; make an
   evidence-only commit if tracked evidence belongs in that repository, then push.
5. Nereus: bind the real final fork, typed artifact/image/focused-test receipts, update O1 status and linked current
   docs, rerun documentation/foundation gates, commit and push.

Server receives no branch, commit, or push. Any failed mandatory gate stops status promotion and is recorded without
rewriting history.
