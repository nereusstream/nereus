# ADR 0006: Make v0.2 a Clean Break from v0.1

- Status: Accepted
- Date: 2026-08-08
- Scope: Nereus `main` beginning with `0.2.0-SNAPSHOT` and coordinated Nereus Pulsar/Kafka integration work

## Context

Nereus v0.1 established the first complete product, Pulsar, and native Kafka storage paths. The project has no
external customers or deployed compatibility commitment yet. Carrying deprecated facades, dual implementations,
legacy readers, and migration logic into the next core-path design would therefore add permanent complexity before
there is a user who benefits from it.

The V1 implementation must still remain reviewable and reproducible. The product repository also has a historical
`v0.1.0` branch with release-only benchmark and source-lock history that must not be deleted or rewritten as part of
the new branch cut.

## Decision

1. Preserve the final V1 product line on `refs/heads/v0.1`, cut from
   `main@d599ea40d9c49a1fef4474d60f985d6fa3f366f2` and frozen with product version `0.1.0`.
2. Retain the historical `refs/heads/v0.1.0` branch unchanged until its release-only history and benchmark evidence
   have been audited. It is not the base of the new `v0.1` line.
3. Preserve the exact V1 integration sources on `nereus-V1` branches in the organization forks:
   - Pulsar: `11d7ab15291ca4bbc9cc29dedd7878c4e1311ec9`;
   - Kafka: `76f62f3b83e882105219b6c7687dbde594a8b8a2`.
   Full commit ids, not branch names, remain the build and release authorities.
4. Advance Nereus `main` to `0.2.0-SNAPSHOT`. V2 may replace or delete V1 source and binary APIs directly. Superseded
   APIs receive no deprecation-only wrappers, compatibility facade, dual runtime, or migration reader by default.
5. V2 is a fresh-deployment line. A V2 process must not attach to a V1 Oxia namespace, Object Store prefix, Kafka
   feature state, checkpoint family, or other durable identity whose changed bytes it could misinterpret.
6. Every changed durable contract receives a distinct, previously unused format version, type discriminator,
   namespace, or object prefix as appropriate. Detection of V1 state on a V2-only path fails closed with a diagnostic.
7. Product V2 is not a mechanical rename of every class containing `V1` or `V2`. Existing codec names describe their
   own wire/schema generations. Unchanged formats retain their existing identifiers; changed formats advance based on
   their individual version histories.
8. M1 ends with a pure V2 active Gradle/BOM/publication/CI graph. It contains no compilable, publishable, or runnable
   V1 runtime, deprecated shim, Phase/F9 task, or V1-only script. KoP runtime leaves the active graph while its design
   documents remain. The transition first lands the V2 domain/SPI and boundary checks, then cuts settings/BOM/publish/
   CI edges, and finally removes the large V1 runtime and historical gates in separate mechanical commits. The
   architecture replacement, gate rewrite, and roughly thousand-file deletion are not collapsed into one review.
   Protected `v0.1`/`v0.1.0` history is the source reference for removed implementation.

## Consequences

- Core-path work can optimize for one V2 design instead of maintaining two operational models.
- There is no supported in-place upgrade, rollback, mixed V1/V2 cluster, or shared durable namespace between the two
  product lines. V2 validation uses newly provisioned metadata, object, and broker state.
- Cross-repository changes must update Nereus, Pulsar, and Kafka source locks together and preserve their V1 branches.
- Tests must prove both the intended V2 path and fail-closed rejection at every V1/V2 durable boundary that changes.
- Historical documentation and golden vectors remain where they are evidence; they are not changed by a global
  `V1`-to-`V2` or `0.1`-to-`0.2` replacement.
- `main` may temporarily expose only the implemented V2 milestone graph while later V2 data-path modules are rebuilt;
  M1 Final is nevertheless fail-closed on any surviving active V1 edge.

## Release boundary

The branch-cut evidence and exact V1 source tuple are recorded in [`../releases/v0.1.0.md`](../releases/v0.1.0.md).
An annotated `v0.1.0` tag and release artifacts remain separate, gated publication actions.
