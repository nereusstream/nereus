# ADR 0015: V2 0.2 Storage Epoch runtime scope

## Status

Accepted for the 0.2 release scope. This ADR refines ADR 0012; implementation and runtime evidence are not started at
M0.

## Context

ADR 0012 defines an append-only Storage Epoch chain so one Topic Protocol Binding can evolve physical placement at
exact protocol-native frontiers. Shipping an online profile transition also requires a distributed drain, seal,
activation, recovery, rollback, historical-materialization, retention, and GC protocol. Pulsar BookKeeper/Object
evolution additionally has to preserve ManagedLedger ledger-chain, MessageId, cursor, and offload semantics.

The 0.2 product must first replace the V1 append correctness model, make Kafka stronger than the pinned AutoMQ baseline,
and keep the Pulsar path at least as strong as pinned native Pulsar. Online cost/performance switching is not required to
prove those core paths.

## Decision

0.2 persists the Storage Epoch identity and append-only chain model and enforces binding-scoped typed frontiers plus the
single-admitting-epoch invariant. The 0.2 runtime creates exactly one initial Storage Epoch for each new Topic
Incarnation and does not expose:

- an online profile-transition API or operator command;
- a transition coordinator or drain/seal/activate-new-epoch state machine;
- same-incarnation profile replacement;
- transition-driven historical backfill or retirement of an old profile.

The initial profile remains a topic-level choice. Different Topic Incarnations may use different profiles, but changing
an existing incarnation from cost-first Object WAL to a BookKeeper profile, or in the reverse direction, is outside the
0.2 runtime.

The durable model must not collapse back to a lifetime profile flag. Its epoch identity, typed frontier shape, and
append-only/single-writer invariants remain explicit so a later release can add transitions without inventing a second
incompatible metadata model. This model allowance is not permission for 0.2 code to create a second epoch.

## Consequences

- 0.2 users cannot switch an existing Topic Incarnation online between cost-first and performance-first storage.
- `V2-OPEN-MIGRATION-01` is resolved for 0.2. Exact transition states, historical-data policy, and Pulsar
  BookKeeper/Object evolution remain deferred future design questions and do not block the 0.2 release.
- M1 must prove initial-epoch creation, immutable profile fields, typed frontier validation, and rejection of a second
  append-admitting epoch. It does not claim an online transition matrix.
- A future transition feature must close the deferred state-machine, backfill, rollback, and protocol-specific gates
  before implementation; ADR 0015 does not pre-approve any transition.

This decision is tracked by `T-MIGRATION-01`, `V2-MIGRATION-001`, and the deferred questions in
[V2 open questions](../v2/open-questions.md).
